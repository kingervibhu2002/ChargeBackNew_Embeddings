## What problem is this file actually solving?

Picture a small online merchant. A customer disputes a payment with their bank — maybe they say "I never got this," maybe "I never agreed to this charge." The bank claws the money back from the merchant immediately, before anyone has proven anything. The merchant now has a limited window to either **fight** (submit evidence arguing the claim is wrong) or **accept the refund** (let it go). Getting this decision wrong costs real money either way — fighting a case you'll lose wastes an evidence filing fee and time; accepting a case you could have won means giving away money you didn't have to.

Most merchants aren't chargeback specialists. They don't know that a Visa "13.1" claim needs delivery proof, that a RuPay "U002" claim needs proof of a single credit (not delivery proof at all), or that some dispute codes can never be won no matter what evidence exists. `chargeback_agent.py` is the part of this project that stands in for that expertise — a conversation partner that asks the right follow-up questions, checks the merchant's evidence against what actually matters for *their specific* dispute code, and either drafts a rebuttal letter or explains clearly why accepting the refund is the right call.

## The one-paragraph mental model

Instead of one giant "figure everything out at once" AI call, this file breaks the job into **small, single-purpose steps** — extract the reason code, check what evidence exists, decide fight-or-refund, write the letter, double-check the letter isn't making things up — and only calls an AI model for the steps that genuinely need judgment. Steps that are really just "look this up" (deciding fight-vs-refund for a *known* reason code, extracting a reason code that's spelled out in the text, checking whether a claim is even a valid chargeback) are answered with plain Python logic instead — faster, free, and, crucially, **consistent**: the same evidence for the same code always produces the same answer, which an AI model asked to reason about it fresh every time cannot promise. Where a step genuinely needs to understand free-form human language — "did the merchant actually answer the question," "what is this reason code's evidence requirement," "write a persuasive rebuttal letter" — that's exactly where an AI call is used, and used narrowly, for one job at a time.

## `DisputeAgent` — what the class actually holds

Everything in this file lives on one class, `DisputeAgent`, created once when the server starts and reused for every request (creating it fresh per request would mean reconnecting to the vector database and rebuilding the whole graph on every single message — wasteful and unnecessary, since none of what it holds is request-specific).

```python
class DisputeAgent:
    def __init__(self, store, embed_fn, rerank_fn=None, checkpointer=None):
        self._store         = store          # the shared connection to the knowledge base
        self._embed         = embed_fn       # turns text into a vector for similarity search
        self._rerank        = rerank_fn      # optional: re-scores search results for better ordering
        self._checkpointer  = checkpointer   # optional: LangGraph's save/resume mechanism (see §7)
        self._llm, self._fallback_llm = _make_llms()   # primary + backup AI model
        self._graph         = self._build_graph()      # the actual step-by-step workflow (§5)
        self._list_cache    = {}             # remembers recent list/compare answers, cheaply
```

Nothing here is specific to one conversation — `store`, `embed_fn`, and the two LLM clients are shared infrastructure, injected in from `api_server.py` rather than created inside this class, specifically so the whole app only ever opens **one** connection to the vector database (its storage format only allows one process/connection at a time — see `README.md`'s Running section).

**Why two LLM clients (`_llm` and `_fallback_llm`)?** Real API calls sometimes fail — a rate limit, a timeout, a model temporarily overloaded. Every call in this file goes through `_invoke()` (or `_invoke_with_tools()` for the tool-calling paths in §6), which tries the primary model first and silently falls back to a second, smaller model if it fails:

```python
def _invoke(self, messages: list) -> object:
    try:
        return self._llm.invoke(messages)
    except Exception as primary_err:
        try:
            return self._fallback_llm.invoke(messages)
        except Exception:
            raise primary_err
```
Every node that needs the AI calls this one method instead of touching a model directly, so this safety net is automatic everywhere — no individual step has to remember to implement its own retry logic.

## `ChargebackState` — the shared notebook

Every step in this file's workflow reads from and writes to one shared piece of data — `ChargebackState`, a Python `TypedDict` (a dictionary with a fixed, documented set of keys). Think of it as a form that starts almost entirely blank and gets filled in, one field at a time, as the conversation progresses — no single step ever sees or fills in the whole thing at once.

| Field | What it holds | Filled in by |
|---|---|---|
| `user_query` | The merchant's message, with any personal data masked out | Set at the start; occasionally rewritten by the conversational layer (§6) |
| `additional_context` | Whatever the merchant said on a follow-up turn | Passed in from the previous response |
| `merchant_id` | Who's asking, resolved server-side — never trusted from the message itself | `api_server.py`, before the graph even starts |
| `query_type` | `"dispute"` / `"question"` / `"escalation"` / `"invalid"` | The first step, `validate_node` |
| `reason_code` / `card_network` | e.g. `"13.1"` / `"Visa"` — which specific claim this is | `planner_node`, refined later if still unknown |
| `retrieved_docs` | Relevant policy text pulled from the knowledge base | `planner_node` |
| `retrieval_status` / `retrieval_issues` | `"good"` / `"ambiguous"` / `"bad"` / `""` — were the retrieved documents actually consistent with the detected network, or just semantically similar to it? Signal only right now; nothing yet retries retrieval or blocks generation when this comes back `"bad"` | `planner_node`, via `retrieval_evaluator.py` |
| `is_settlement_issue` | Is this actually a missing-payment problem, not a real chargeback? | `detect_settlement_node` |
| `evidence_present` / `evidence_missing` | What the merchant has, mapped to a fixed vocabulary (see [`DECISION_RULES_GUIDE.md`](DECISION_RULES_GUIDE.md)) | `extract_evidence_node` |
| `needs_more_info` | Should the graph stop and ask the merchant something? | Several nodes |
| `decision` / `decision_reason` | `"fight"` or `"refund"`, and why | `decide_node` |
| `draft_response` | The letter or refund guidance, before final polish | `generate_node` |
| `confidence_score` / `is_grounded` / `groundedness_issues` | A trustworthiness check on the final answer | `reflect_node` |
| `final_answer` | What actually gets shown to the merchant | Whichever node ends the conversation |

A step never returns the *whole* state — it returns only the fields it wants to change, and the framework merges that on top of everything already there. (No step in this file uses anything fancier than plain overwrite-on-write for that merge — see `LANGCHAIN_LANGGRAPH_GUIDE.md`'s concept-coverage section for the precise mechanics of why that matters.)

## The graph, step by step, in plain language

```
validate → planner → detect_settlement ─┬→ ask_user (END)
        ↘ answer_question (END)          ├→ decide → generate → reflect → END
        ↘ END                             ╰→ extract_code → detect_clarification ─┬→ answer_clarification → ask_user (END)
                                                                                     ╰→ extract_evidence ─┬→ ask_user (END)
                                                                                                            ╰→ decide → generate → reflect → END
```

Twelve steps, each doing exactly one job. Reading left to right is reading the actual order a real dispute gets handled in:

**1. `validate` — is this even a real dispute, and is it safe to process?**
Before anything else: is the message a reasonable length (not empty, not a 5,000-word essay)? Does it look like an attempt to manipulate the AI rather than describe a real problem (a "prompt injection" check)? Any personal data (card numbers, phone numbers) gets masked out before any further processing sees it. Then: is this actually describing a dispute, asking a general question, asking to talk to a human, or nonsense? This step also houses the entire conversational continuity feature described in §6 — case listing, case selection, and follow-up questions are all resolved *here*, before the rest of the pipeline below ever runs, because a resolved conversation can skip straight to a full answer without needing any of the following steps.

**2. `planner` — what is this dispute, and what does policy say about it?**
Pulls out the card network and reason code if they're spelled out in the text (plain pattern-matching — "Visa 13.1" is unambiguous, no AI judgment needed), then searches the knowledge base for relevant policy. If the merchant names a real case ID they've filed before, this step looks up the actual database row and grounds everything downstream in the real facts of that case instead of guessing from free text. Only if none of that works — no code, no network, nothing usable extracted — does this step ask an AI model to take a guess from the raw text. It also runs a quick, deterministic sanity check on what it just retrieved — do these documents actually belong to the network just detected, or did they just happen to score well on similarity? (See `retrieval_evaluator.py`, below.) A high similarity score doesn't guarantee policy applicability — a Visa document about "unauthorized transactions" can score well against a UPI fraud question while being the wrong network's rules entirely.

This case-ID lookup is scoped to the caller's own `merchant_id` (a merchant can't probe another's case by guessing its ID) — but two real bugs, both found live, once lived in what happened next. **First:** when the ID matched no row for this merchant — a typo, or a real case belonging to someone else — this step used to just silently do nothing, leaving the reason code "Unknown" and letting the conversation fall through to `extract_code`'s generic "did a customer file a chargeback against you?" intake question, as if no case ID had ever been mentioned at all. Confirmed live: a merchant asking about another merchant's real case ID got that exact generic question back, with no acknowledgment that a case ID was even seen — reading as if the system had ignored what they typed. Fixed with a new `case_ref_not_found` state field, checked by `extract_code_node` before it falls back to the generic question, so the merchant now gets an accurate "I couldn't find a case matching that ID on your account" — worded identically whether the ID is simply wrong or belongs to a different merchant, so it never confirms or denies that someone else's case exists. **Second, once a case is actually found:** for U002 specifically, this step already runs the same bank-ledger analysis (`chargeback_analysis.analyze_chargeback()`) `cbs.py`'s Phase 2 reconciliation logic backs — but that analysis used to only get inserted into `retrieved_docs` as *text*, hoping the AI model in `extract_evidence_node` would notice it and correctly conclude the merchant's evidence requirement was already satisfied. Confirmed live it wasn't reliable: a case where the ledger had already confirmed "exactly one reconciled credit, fight" still got asked to "confirm only one credit was issued" — the exact fact the system itself had already verified, from a more authoritative source than anything the merchant could self-report. Fixed with two more explicit state fields, `ledger_decision`/`ledger_decision_reason` (set when `analyze_chargeback()` returned a confident action) and `ledger_no_decision_reason` (set when it found a real blocker instead — a pending ledger entry, a settlement mismatch — that no merchant-supplied evidence could resolve either way). Both are checked deterministically by `extract_evidence_node` and `decide_node`, bypassing the LLM's evidence-guessing and the rule table's evidence-free default entirely for these cases — the same "deterministic beats AI judgment wherever the task allows it" principle this file uses everywhere else, applied here specifically because trusting the LLM to re-notice its own planted fact was the thing that failed.

**3. `detect_settlement` — wait, is this even a real chargeback?**
A surprisingly common confusion: a merchant sees money missing and assumes it's a chargeback, when actually the customer's payment simply never went through (a "settlement failure," a completely different problem with a completely different fix). This step is a single keyword check — no AI call — that flags this case so `decide_node` can hand back the right advice instead of chargeback-fighting advice for a chargeback that never happened.

**4. `extract_code` — do we actually know what claim we're dealing with?**
If the previous step didn't find a reason code, this one gives the merchant's follow-up reply a second chance to supply it. If it's still unknown, the conversation pauses here and asks for it — there's no way to give correct advice about "some unspecified dispute."

**5. `detect_clarification` — is the merchant answering, or asking something back?**
A one-line check (not an AI call): does the merchant's reply *look like a question* ("what does that mean?") rather than an answer ("yes, we have delivery proof")? This decides whether the next step is *answering* them or *extracting evidence from* them — two very different things that would otherwise get confused.

**6a. `answer_clarification` — answer the merchant's actual question.**
If they asked something, this step answers it — and specifically checks whether the case's own real, on-file facts (pulled in step 2, if a real case was named) already answer part of the question, leading with those before falling back to generic advice. A live bug this fixed: a merchant asking "can you check my data and tell me if two amounts were credited?" was getting told *how* to go check their own bank statement, even when the system already had that exact case's status sitting right there — this step now checks for and uses that first.

A second live bug, found later: the closing line this step adds was a single hardcoded "come back with evidence once you have it" — right for the evidence-gathering stage, wrong everywhere else. Confirmed live: a merchant who asked "what is a reason code?" *before* ever providing one got told to come back with evidence, when the actual blocker was the reason code itself — there was no evidence stage to return to yet, and nothing tracked what was originally being asked once this step's own answer overwrote it. Fixed by making the closing line conditional on the same deterministic signals `extract_code_node`/`decide_node` already use: reason code or network still unknown → ask for the reason code instead; `ledger_decision` already set (the bank's own ledger settled this case, no evidence needed at all) → say so, don't ask for evidence; otherwise → the original "come back with evidence" framing, unchanged.

**6b. `extract_evidence` — what does the merchant actually have?**
Reads the merchant's free-text answer and maps it onto a fixed, closed vocabulary of evidence types ("tracking number," "AVS match," "confirmed only one credit was issued," etc. — see [`DECISION_RULES_GUIDE.md`](DECISION_RULES_GUIDE.md) for the full list and why it's closed rather than free text). When a deterministic rule already exists for this exact reason code, this step tells the AI model *exactly* which evidence types matter for this specific case — instead of making it guess from a flat list of thirty possibilities, most of which are irrelevant to any one dispute.

**7. `decide` — fight or refund?**
For a settlement-failure case (step 3), this returns settlement-specific advice, not a fight/refund call at all. Otherwise: check the hand-curated rule table first (`decision_rules.py`, its own full write-up) — if this exact reason code has a documented evidence requirement, the answer is computed by a plain lookup, no AI judgment involved, and it's *always* the same answer for the same evidence. Only reason codes with no such rule fall through to an AI model's judgment call.

**8. `generate` — write the actual letter (or refund guidance).**
Drafts the rebuttal letter for a "fight" decision (pulling in real example rebuttal letters from the knowledge base as structural templates) or clear refund guidance otherwise. A fight response always gets a legal disclaimer appended, reminding the merchant this is guidance, not a guarantee, and to verify with their actual payment processor.

**9. `reflect` — is this letter actually trustworthy before we show it to anyone?**
The last step before the merchant sees anything. Scans the draft for any reason code it mentions and checks that code actually appears in the retrieved policy documents or the rule table — a code mentioned in the letter that traces back to *neither* is a strong signal the AI invented something. Computes a 1–10 confidence score from a plain formula (how much real evidence was found, whether a deterministic rule existed, whether the code was actually confirmed) rather than asking the model to rate its own answer. This step calls no AI model at all — it's pure verification logic, on purpose: you don't want the same kind of system that might hallucinate a fact to also be the one certifying that it didn't.

**A real gap found live, since fixed:** this check only ever covered reason codes — never the case_id/UTR the letter itself cites. A fully-grounded letter (correct reason code, real ledger evidence, correct UTR) still cited the wrong case_id in its own "Re:" line — a real, live example garbled `NPCI20260530M002010` into `NPCI20260530M010` (a dropped "002"), and reflect_node's existing checks had nothing that would ever catch it, since it only scans for reason-code tokens. This matters more than an ordinary wording slip: this letter is meant to actually go to a bank, and a wrong case reference in it is a real, external consequence, not just an awkward sentence. Fixed by having `planner_node` also record `resolved_case_id`/`resolved_utr` (the real values for whatever specific case was named), and having `reflect_node` scan the draft for any `NPCI\w+`/`UTR\w+`-shaped token that doesn't match them — and, since there's only ever one real case being discussed in a given letter, *correcting* it outright rather than merely flagging it (a lower confidence score is easy to miss buried in a long letter; a wrong case ID sent to a bank isn't something to leave for the merchant to notice). The correction is deterministic string substitution, not another AI judgment call — consistent with why this step calls no AI model at all in the first place.

Two more steps sit outside this main flow: **`ask_user`** simply packages up whatever question the current step needs answered and ends the conversation for this turn, waiting for the merchant's reply. **`answer_question`** is a separate, lighter path entirely — for a merchant who's just asking a general knowledge-base question ("what's the difference between Visa 10.4 and 13.1?") rather than describing an actual dispute, this step searches the knowledge base directly and answers in one AI call, skipping the whole fight/refund pipeline above since there's no specific case to evaluate. Its comparison-question branch has one honesty rule worth knowing: this project's knowledge base only covers card networks and NPCI/UPI — not payment gateways/aggregators (Cashfree, Razorpay, PayU) — and a three-way question naming one of those ("how do RuPay, Cashfree, NPCI differ?") used to silently answer only the covered pair and drop the rest with no acknowledgment, since two recognized keywords ("rupay", "npci") were already enough to satisfy the comparison branch's own trigger condition. Fixed by instructing the model explicitly to check the question against what's actually in the retrieved documents and say so plainly when something named isn't covered, before answering the part it can — the same "say plainly when something isn't on file" pattern already used in `_answer_clarification_node` (§5, step 6a), applied here too.

A second, related honesty rule: `is_upi_context()` already stops the model from blending Visa/Mastercard terminology into a UPI-specific answer, but only fires when the query itself names UPI/RuPay/NPCI. A question naming NO network at all ("How to prevent chargebacks?") got neither guard — and every real merchant transaction this platform actually has on file is a RuPay/NPCI UPI transaction (`merchant_db.py`'s schema is RuPay by construction), while the knowledge base's cross-network "best practices" content freely mixes in card-only mechanisms (3-D Secure, AVS, CVV, PSD2 SCA) with no UPI equivalent at all. Confirmed live: this exact question got AVS/CVV/3DS presented as directly actionable advice, with nothing indicating that a RuPay/UPI merchant's transactions never go through card verification in the first place — not hallucinated (the source document is real), just presented without the one caveat that actually matters here. Fixed with a second branch alongside `is_upi_context()`'s: when no network is named at all, the model is told to flag which recommendations are UPI-applicable versus card-network-only rather than presenting every retrieved recommendation as uniformly actionable — confirmed live this changed the answer's own fraud-prevention section from AVS/CVV/3DS to device fingerprinting and blocklists instead, without needing to name what it was excluding.

## The conversational layer: listing cases, picking one, asking follow-ups

Everything above assumes the conversation is a straightforward "describe your dispute → answer follow-ups → get a letter" exchange. Real usage is messier: a merchant might say "show me my open chargebacks," then "tell me about the first one," then ask an unrelated question, then come back to the case they were just discussing. All of that is handled inside `validate_node` — the very first step — using a genuinely different technique from everything described above: **the AI model itself decides what the merchant means**, via real tool calling, rather than pattern-matching their words.

**Why this needed a different approach.** Detecting "does this message want to see the merchant's own cases" started as plain keyword matching, like everything else in this file — and kept breaking. "What all U002 cases exist currently?" would slip past one version of the check; "how much is outstanding this month?" would slip past another. Every fix caught one phrasing and missed the next, because natural language for "show me my stuff" genuinely has no fixed, enumerable pattern the way a reason code (`U002`, `13.1`) does. So this one decision point hands the judgment to the model instead: it's given two tool "options" — *list my cases* or *look up a computed number* — with a plain-English description of when to use each, and it picks (or picks neither, if the message isn't actually about the merchant's own data at all). Full mechanics of how this works — `@tool`, `.bind_tools()`, the multi-round loop needed for the richer case-detail feature below — are in [`LANGCHAIN_LANGGRAPH_GUIDE.md`'s tool-calling section](LANGCHAIN_LANGGRAPH_GUIDE.md#16-tool-calling--letting-the-model-ask-for-real-data).

**A real gap this decision point has, found live:** it only ever runs when `pendingQuery` (the browser's persisted original query — see below) *doesn't* already name a specific case. Confirmed live it needed exactly that guard: a merchant who'd already been answered on one exact case ("Help me with case NPCI20260530M002010") asked a genuine, substantive follow-up on it ("step by step, when was it raised, what's the reason code, what evidence...") — and the tool-calling decision, asked to classify the ORIGINAL `pendingQuery` text, misread it as a *list my cases* request (its own docstring says "use this when the merchant wants to SEE or SELECT a case," which a specific-case mention loosely resembles). Once misclassified, the follow-up didn't look like an ordinal selection against the resulting list either, so the existing "abandon and promote the latest reply" fallback (§ below) took over — discarding the case reference in `pendingQuery` entirely and replacing it with the follow-up text alone, which named no case, no reason code, nothing. The merchant got the generic "did a customer file a chargeback against you?" intake question, as if the whole prior exchange had never happened. Fixed with a new `classifier.has_case_reference()` check, gating this whole block: a `pendingQuery` that already names one exact case skips the list-detection decision entirely, so a genuine follow-up on it now reaches `detect_clarification_node`/`answer_clarification_node` instead, grounded in the same case. A second, smaller gap surfaced in the same trace: that follow-up was itself one long imperative sentence with three embedded questions and no "?" at all ("help me with ..., when was it raised, what is the reason code, what evidence...") — `is_clarifying_question()` only checked the start/end of the text, missing all three. Fixed with a mid-sentence check: a clause starting with a question word right after a comma or semicolon now also counts.

**That `has_case_reference()` fix above turned out to be an over-correction, found live in a later session.** It skips the ENTIRE list-detection block whenever `pendingQuery` already names a case — but that block is also the only place the "abandon and promote a genuine new topic" repair lives. So once a case is named, there was no mechanism left AT ALL to notice the merchant had moved on to a completely different, unrelated question. Confirmed live: after landing on case `NPCI20260530M002010`, asking "which all chargeback cases are currently open and deadline is also due not passed?" — a real, different, aggregate question — got the SAME single case's details again, because `detect_clarification_node`/`answer_clarification_node` was the only thing left to route to, and that node's own prompt says to "lead with" whatever case-specific record sits in `retrieved_docs[0]`, which is always the one anchored case no matter what was actually asked. Fixed with a new branch, structurally parallel to the list-repair one: when `pendingQuery` names a case AND the merchant's latest reply itself looks like a data lookup, the same real LLM tool-call (`_resolve_data_lookup_intent`) is asked to classify the FOLLOW-UP text specifically — never the stale case-anchored `pendingQuery`, which is exactly what the `has_case_reference()` guard exists to avoid feeding it. That tool-call alone wasn't reliable enough, though: tested directly, it also misread "help me with step by step info about THIS chargeback" (a genuine, real follow-up on the SAME case) as wanting to see other cases — reintroducing the exact case-losing bug from two paragraphs up, for a different trigger. Fixed with a deterministic veto checked before ever calling the LLM: `classifier.refers_to_current_case()` recognizes a demonstrative reference ("this case," "this chargeback," "that dispute") as unambiguous enough to skip the tool-call decision entirely and stay anchored, no LLM judgment needed to know what "this chargeback" refers to.

**A third kind of follow-up fell through the same crack, one that isn't data-lookup-shaped at all.** "help me with all open questions," typed as a follow-up on the same anchored case, matched none of the existing checks — `looks_like_data_lookup()` needs a "case"/"chargeback"/"dispute" keyword ("open questions" has neither), it's not an escalation phrase, and it doesn't reference the current case either. With nothing to catch it, it fell through to being silently treated as evidence — and since this case's `ledger_decision` was already set, `extract_evidence_node` short-circuits straight past evidence-gathering regardless of content, producing a complete rebuttal letter for a message that never asked for one. Fixed with a new `classifier.looks_like_new_request()` check: an imperative opener ("help me with...", "show me...", "list...") at the START of the text is unambiguous enough to promote directly, no LLM confirmation needed — deliberately anchored to the *start* only (`re.match`, not `re.search`), since a genuine evidence answer can legitimately contain words like "show" mid-sentence without being a new request. Both this and the data-lookup branch share the same `refers_to_current_case()`/`is_junk_reply()` guards, so none of the three fixes in this section compete with each other.

That opener check turned out to be too broad in the opposite direction, found live in the exact same conversation shape it was built for: "help me with **it**" — a merchant confirming they want to continue with the case just introduced, not asking about something else — also starts with "help me with," so `looks_like_new_request()` promoted it too, discarding the case-anchored `masked_query` and replacing it with the bare, contentless "help me with it." `classify_query_type()` on that alone is `"invalid"`; normally `_validate_node`'s own "invalid + context" rescue would recover from this by reclassifying `original_masked_query` + the latest reply, but here `masked_query` itself (not just `additional_context`) had already been degraded to the same throwaway text, so the LLM substantive-context backstop judged the "context" non-substantive too, and the rescue's own precondition (`context` truthy) never held. The merchant got the generic "please describe a chargeback dispute" rejection on a conversation that was already three messages deep into a real one. The same shape hit an unlucky typo too — "help me withis" (missing a space/letters from "help me with this") — which normalizes to the identical failure. Fixed with `classifier._VAGUE_ANAPHORIC_HELP_RE`: `looks_like_new_request()` now also checks whether the ENTIRE opener-matched text is nothing more than "help me" (+ optional "with"/"to") + a bare pronoun ("it"/"this"/"that"/the "is" typo remainder) and no concrete subject — if so, it's read as pointing back at whatever's already anchored, not a new ask, and `masked_query` is left untouched. "help me with all open questions" still promotes correctly (there's real content after the opener); only the subject-free case was ever the bug.

**A fourth kind of follow-up fell through the same crack: not a new topic, not the same case's evidence — a request to stop entirely.** "I have a chargeback and I want to talk to a human agent," typed as a follow-up on an already-anchored U002 case, produced a complete rebuttal letter. Root cause: `classify_query_type()` — the function that recognizes an escalation phrase ("talk to a human agent," "connect me," "speak to") at all — is only ever called on `masked_query` at Guard 4, further down this function. A named case in `masked_query` always classifies as `"dispute"` via `_CASE_REF_RE`'s own precedence, regardless of what the merchant's actual reply said, so `additional_context` never got checked for an escalation phrase at all — the existing "invalid → retry combined" rescue nearby only fires when `masked_query` itself classifies as `"invalid"`, never `"dispute"`. Fixed with an early, unconditional check, ahead of the case-reference/list-continuity logic entirely: the LATEST reply segment is classified on its own, and an escalation verdict short-circuits immediately to the same human-support message the first-turn path already gives — now a shared `_ESCALATION_MESSAGE` class constant so the two copies can't drift.

**The list it correctly promoted to still had a real gap.** That "which all chargeback cases are currently open and deadline is also due not passed?" example above got fixed twice — first for losing the case anchor, then for what the resulting list actually contained. `_filtered_open_cases()` (shared by the case-selection continuity flow and `_answer_question_node`'s own listing branch) only ever filtered by `status='Open'` — which does NOT mean the deadline hasn't passed, a separate field this demo data doesn't keep in sync with status. Confirmed live: the list included cases with a `response_deadline` weeks in the past, silently ignoring the "deadline not passed" half of the question — `text_to_sql.py`'s own NL→SQL path already handles this correctly (its rule 7, for "due in N days"/"expiring soon" phrasing), but the deterministic listing path used here had no equivalent. Fixed with `classifier.looks_like_active_deadline_filter()` — deterministic, same reasoning as `looks_like_aggregate_question()`: requires both a deadline word and a temporal-status word ("passed," "remaining," "still") together, not either alone — feeding a new `active_deadline_only` parameter through `_filtered_open_cases()` at all three of its call sites.

**That keyword regex turned out to be too brittle on its own, found live almost immediately after.** "tell open cases for which dealine is not surpassed?" — a genuine typo/synonym away from the phrasing above ("dealine" for "deadline," "surpassed" instead of "passed") — matched neither `_DEADLINE_WORD_RE` nor `_DEADLINE_STATUS_WORD_RE` at all, silently returning every open case again. This is the exact class of problem this project has hit and fixed the exact same way before (`_resolve_data_lookup_intent()`'s own module comment: regex-guessing natural language "abandoned after four distinct live failures... replaced with real LLM tool-calling"), and `reason_code` on the same `list_merchant_cases` tool already proves the pattern works — the LLM reliably extracts it as a tool argument across arbitrary phrasing, typos included, in a way no keyword list can keep up with. Fixed by giving the tool a matching `active_deadline_only: bool` parameter instead of relying on the regex alone: the model now decides it directly, the same way it already decides `reason_code`, OR'd with the regex (kept as a deterministic floor, not replaced — a false negative from a genuinely non-deterministic LLM call on live-tested-correct keyword text shouldn't silently drop the filter). Verified live: the exact misspelled phrasing now correctly returns only the 2 unexpired-deadline cases, and both the correctly-spelled phrasing and a plain listing with no qualifier still work as before.

**Requested directly after seeing that fix's output: the flat list itself gave no sense of urgency.** A case whose deadline passed weeks ago sat visually identical to one due next month — the merchant has to read every `due` date themselves to tell them apart. Added an urgency summary line ("N deadline already passed, N due within the next week, N with more than a week remaining") plus a per-case `— DEADLINE PASSED` / `— due within a week` tag, computed by a new `_deadline_bucket()` helper. Deliberately doesn't reorder or regroup the list itself — `_filtered_open_cases()` already sorts by `response_deadline ASC`, which happens to already be overdue-first/soonest-first, so the numbered positions a later "the first one" resolves against never change. Verified live for both the summary content and that ordinal selection still resolves correctly against the same list.

**That summary immediately surfaced a nonsensical recommendation sitting right next to it.** The closing "want to start with that one?" line always suggested `cases[0]` — the chronologically-earliest deadline overall, per the existing sort order — without checking whether that deadline had actually passed. With 5 of 7 cases already overdue, this suggested starting with the MOST overdue case of all, immediately contradicted by its own "— DEADLINE PASSED" tag one line above. Fixed to suggest the earliest deadline that HASN'T passed instead (falling back to an honest "all N of these are already past their response deadline" when none remain) — the ordinal numbering itself is untouched, so "the first one" still means list position 1, not the recommended case; verified live these two are correctly independent (recommendation pointed to case #6, "the first one" still resolved to case #1).

**Two more gaps found via a systematic eval, not a single live trace this time.** A merchant-proposed 40-question evaluation design (distinguishing authoritative case/ledger facts from RAG policy knowledge from deterministic decisioning) was adapted into `agent_eval.py` — a real, runnable suite against this project's actual reason codes/statuses/cases instead of the fictional schema it was originally written against — and run directly against `DisputeAgent` (bypassing the HTTP layer and its rate limiter). It surfaced two real bugs neither of us knew about:

1. **Continuity repair was wired only for `list` intent, not `aggregate` intent.** `_validate_node`'s "resolve a case selection / catch an out-of-range reference / abandon and promote a genuine new topic" block only ever runs inside `if list_intent is not None:` — so a session that opened with a computed-number question ("How many chargebacks do I currently have?", `_resolve_data_lookup_intent()` returns `type: "aggregate"`) had **no** continuity repair at all. `masked_query` stayed frozen as that exact original question for every later turn, no matter what the merchant actually asked next. Confirmed live via the eval: three different real follow-ups in one session ("how much is still open?", "what are my most common reasons?") all returned the byte-identical first answer. Fixed by tracking a broader `data_lookup_intent` (any type) alongside the narrower `list_intent`, and adding an `elif data_lookup_intent is not None:` branch that applies the same "promote a non-junk follow-up" repair — the only piece of the list-branch logic that actually makes sense for a non-list intent too (case-selection/out-of-range have no meaning without a list to pick from).

2. **A first-turn question about an already-named case got a generic decision letter instead of an answer.** `is_clarifying_question()` — the only signal that routes to `answer_clarification_node` instead of the evidence-gathering pipeline — only ever checked `additional_context`, a SECOND-turn reply. A first message like "I have received a chargeback for case NPCI... What exactly happened?" has no `additional_context` yet; the question IS the query. Confirmed live: this and a "Did you receive my evidence?" first message both got a full generic rebuttal/refund letter, never actually answering what was asked — and for an already-Lost case, "Just move it to pre-arbitration" (an instruction, not phrased as a question at all) got the same treatment: silently ignored, not confirmed and not denied, just another unrelated letter. That specific instruction-shaped case still isn't caught by this fix (it needs a genuine escalation-eligibility deterministic check — this project doesn't have one, and per its own encyclopedia, NPCI's UPI process has no pre-arbitration/arbitration ladder like card networks do, so the honest answer for a U-code isn't "yes" or "no," it's "this concept doesn't apply here" — a separate, not-yet-built piece of work). What IS fixed: a new `resolved_case_id` state field, set by `planner_node` whenever a named case resolves to a real row (regardless of whether a confident ledger/rule decision was reached), lets `detect_clarification_node` also check the first-turn `user_query` itself — but only when a real case was already resolved, so an ordinary new dispute description that happens to contain a question word isn't misrouted away from normal evidence-gathering.

Both fixes verified via `pytest` (deterministic suite, unaffected) and syntax checks; live re-verification of these two specifically is pending — Groq's daily token quota (200,000 TPD, shared across every call this project makes, not just this session's testing) was exhausted mid-verification.

**Picking a case gets a real, grounded introduction, not a bare evidence question — however the case is named.** When a merchant picks a case ("the first one," "#2," a case ID), the system doesn't just jump straight to asking for evidence. `_build_case_intro()` runs a real, multi-step lookup — fetch the case's actual database row (amount, status, deadline, reason code), then fetch what that reason code actually means and requires from the knowledge base — and stitches both together into one grounded, natural-language introduction before asking for anything. This needs *two* rounds of AI decision-making, not one, because the second lookup (what does this reason code require) can't happen until the first one (what is the reason code) has already returned an answer — verified live before this was built, in that early test, the model correctly refused to guess the second one early. That turned out not to be reliable, though — see the reason-code-mismatch bug below for what happened when it later did guess.

For a while, this only happened when the case came from *picking one off a list*. A merchant who instead named a case directly in their first message ("Help me with case NPCI20260530M002010") hit a completely different code path — `_planner_node`'s step 4b — which grounded the reason code correctly but then fell straight through `extract_evidence -> decide -> generate`, producing a full fight/refund letter as the FIRST thing the merchant saw, regardless of what they'd actually asked. Same case, same merchant, a materially worse experience purely because of *how* the case was referenced — flagged directly by the person who'd been testing this all session, in almost exactly these terms: "the moment I ask about any transaction, you jump straight to a conclusion." Fixed by moving the direct-mention check into `_validate_node` itself, ahead of everything else: a case named directly in a query with no `additional_context` yet (a true first turn) now resolves the row and calls `_build_case_intro()` the same way the list-selection path always has. Only on that first turn — once the merchant has replied with evidence (chat.html resends the same query with `additional_context` now set), this check deliberately doesn't re-fire, and the normal pipeline (still grounded via `_planner_node`'s own step 4b lookup, still gated by the `ledger_decision` short-circuit from an earlier fix) proceeds to a real decision and the actual letter. Verified live end-to-end: turn 1 now returns a case summary + reason-code explanation + evidence guidance with no decision made yet (`needs_more_info: True`, `decision: ""`); turn 2, after the merchant confirms their evidence, correctly produces `decision: "fight"` and the real letter.

**A real gap, found live and fixed, worth knowing about even though it's closed now:** this conversational memory lives entirely in the browser, which resends the whole exchange on every turn (see §7's checkpointer note for why). The browser used to fully reset that memory the moment ANY single question in the conversation got a complete, standalone answer — so a case you were discussing could drop out of context a few turns later, even mid-topic, the moment a fully-answered tangent came in between. Reported live with a real 6-turn transcript (list cases → select one → two follow-up questions → an aggregate question → "what about the second one?") that ended in a flat rejection by the last turn, with nothing left server-side to resolve "second one" against. Fixed in `chat.html`: conversation memory now persists across a completed answer too, capped to the most recent turns rather than growing without bound, and is only actually cleared by a genuine topic change (the existing `looksLikeNewTopic()` check, now applied regardless of whether the agent is mid-follow-up) or switching merchant/tab. Fixing this surfaced a second, deeper bug in the same trace: `classifier.detect_case_selection()`'s clarifying-question guard (added to stop "what does U002 mean?" from false-matching a case by reason code alone) was firing before the ordinal-word check ever ran, so "what about the second one?" — a real selection, just phrased as a question — was being rejected as "just a question" and answered from the wrong (first) case entirely. Fixed by reordering: strong ordinal/number signals are checked first, and the clarifying-question guard now only protects the weaker reason-code-mention match it was actually built for.

Fixing *that* surfaced a third bug, one step further into the same conversation: asking about a case position that doesn't exist ("what about the third one?" with only two cases ever shown) has no case to resolve to at all — `detect_case_selection()` correctly recognized "third" as an ordinal and correctly refused to guess (bounds-checked: index 2 isn't `< len(shown_cases)==2`), returning `None`. But `None` here was indistinguishable from "not a selection attempt at all," so `_validate_node`'s fallback treated it the same way — re-enriching the query with whatever case the *original* `pendingQuery` happened to reference, and confidently answering as if that case were "the third one." A merchant would read a real, fluent-sounding answer about a real case, for a question that should have gotten "you only have 2 cases, there's no third." Fixed with a new `classifier.is_out_of_range_case_reference()` — checked as its own branch in `_validate_node`, before the reattach-and-guess fallback ever runs — so an out-of-range ordinal reference now gets told the truth (the real count, the real list again) instead of a hallucinated-sounding substitution. A smaller, related find in the same pass: `_ORDINAL_WORDS` didn't recognize "forth" (a common misspelling of "fourth") as an ordinal at all, so it hit the same wrong-case bug through a different gap — missing vocabulary rather than a missing bounds check. Added as an alias.

**A fourth bug in the same family: a reference to "some other case," relative to whatever was just discussed, but naming no ordinal at all.** Reported live with a 3-turn transcript: list of 7 open cases → "The second one" (resolved correctly, full case intro shown) → "What about the other one?" — which re-showed the exact same 7-case list from scratch, with no acknowledgment a specific case had just been picked. Root cause: "the other one" has no number or ordinal word in it, so it doesn't match `detect_case_selection()`, doesn't match `is_out_of_range_case_reference()` either (same reason), and fell all the way through to the "abandon and promote a genuine new topic" fallback — which is correct for an actually-unrelated follow-up, but wrong here, since the merchant *is* trying to reference a specific case, just relative to context this project's stateless-per-call design has no way to reconstruct (`chat.html` never tells the server which case a prior turn resolved to — confirmed directly: `api_server.py`'s response has no `user_query` field at all, and `chat.html`'s `pendingQuery` is set once from the client's own first message and never updated from anything the server returns). The first fix attempted — rewriting the `user_query` field in `_build_case_intro()`'s success-path return dict to reference the resolved case — turned out to be inert for exactly that reason; left in as a harmless internal-consistency fix (matching what the failure path already did) but it doesn't touch the client-visible bug. The real fix: a new `classifier.looks_like_relative_case_reference()` check, added as its own branch between the out-of-range check and the promote-fallback, recognizing phrases like "the other one," "a different one," "the previous one" and asking a clarifying question ("Do you mean a different case from the list I just showed? Tell me which one...") instead of either guessing or silently restarting from the list — same "ask, don't guess" principle as `_uncertain()` elsewhere in this file. Verified live: the exact reported 3-turn transcript now produces that clarifying question on turn 3, with no regression on out-of-range references or normal ordinal selection.

**A fifth bug, more serious than the others — confidently wrong information, not just a missed reference.** Reported live: picking the third and fourth cases off a 7-case list (reason codes U007 and U003 respectively) both returned a case summary correctly grounded in the real DB row, immediately followed by an explanation of reason code U005 (fraud/social-engineering) — the WRONG code, contradicting the summary one sentence above it. Root cause traced with a standalone reproduction script (bypassing the live server's Qdrant lock, since `_invoke_with_tools` only needs the LLM, not the store): `_build_case_intro()`'s docstring claimed the model always calls `get_case_details` and `get_reason_code_info` in separate rounds, learning the real reason code from the first before attempting the second — true in the original verification, but not reliable. Confirmed live, repeatably (3/3 attempts): the model sometimes calls BOTH tools in the SAME round, and since it hasn't seen `get_case_details`'s result yet, it guesses a `reason_code` argument for `get_reason_code_info` from the case_id string itself — observed guessing `"M002"` from `"NPCI20260629M002006"`, not a real NPCI code at all (valid codes are U001–U010). Nothing in the knowledge base matches `"M002"`, so `select_domain_chunk()`'s fallback (whatever scores highest in the RuPay domain on raw embedding similarity, once its preferred-reason-code filter comes up empty) picked a dense, generic fraud document instead — the same wrong document both times, since both fabricated codes failed the same way. Fixed two things together: (1) tool calls within a single round are now processed `get_case_details` first regardless of the order the model returned them in, so `network`/`reason_code` are already the real DB values by the time the `get_reason_code_info` branch runs; (2) that branch now prefers those already-known authoritative values over the model's own tool-call argument, not the other way around — the model has no way to know better than the row already fetched, so any disagreement between them is by definition the model being wrong. Verified live: 3/3 repro attempts that previously produced the `"M002"` guess now correctly resolve to the real reason code before the knowledge-base lookup ever runs; the original two-case scenario from the report now returns accurate, code-matched explanations for both U007 and U003.

**A sixth, smaller gap in the same list-continuity family: "last one" wasn't recognized as a case reference at all.** With 7 cases shown, "last one" doesn't match `_ORDINAL_WORDS` (nothing past "fifth"), doesn't match `is_out_of_range_case_reference()` (same, ordinal-word-based), and doesn't match `looks_like_relative_case_reference()` either (that pattern is "other"/"different"/"previous" — "last" isn't ambiguous the way those are, so it was never in scope there). It fell through to the "abandon and promote" fallback, got treated as an unrelated new topic, and was rejected by the generic invalid-query guard — a confusing, unrelated-looking answer for what was actually a perfectly resolvable reference (unlike "the other one," "last" unambiguously means the highest-index case in whatever list was just shown, no clarification needed). Fixed with a new pattern in `detect_case_selection()` itself (`_LAST_ONE_RE`, matching "last one"/"the last one"/"last case"/"the last chargeback"), checked alongside the existing number/ordinal signals so it also resolves correctly when phrased as a question ("what about the last one?"). Verified live: resolves to the 7th case's real U008 details; an unrelated use of "last" ("my last payment failed") correctly still returns no match.

This whole chain is also the clearest real illustration of a structural point worth knowing on its own: `reflect_node` — the only verification step anywhere in this graph — never ran for any of these six bugs. All of them happen inside `_validate_node`'s early-return continuity logic (or, for the fifth, `_build_case_intro()` called from it), which (by design, for speed) routes straight to `END` without ever touching `decide → generate → reflect`. Confirmed live, not assumed: none of the resulting answers were checked for correctness by anything in the graph before reaching the merchant. Even a hypothetically universal `reflect_node` wouldn't have caught the second bug specifically — its check is "does this reason code trace back to real docs/rules," and U002 genuinely does; it was just attached to the wrong case. The fifth bug is the one case in this whole chain a universal `reflect_node` genuinely *could* have caught, in principle — U005 content attached to a U003/U007 case is exactly the "reason code doesn't trace back to what's actually retrieved" mismatch that check looks for; it just never got the chance to run on this early-return path. Verifying *conversational reference correctness* is a different problem than verifying *reason-code groundedness*, and nothing in this graph currently does the former at all.

## Cross-cutting concerns that show up everywhere

A few things aren't tied to any one step — they run underneath most of the file:

- **Guardrails, applied early and often.** Length checks, prompt-injection detection, and PII masking all happen in `validate_node`, before any other logic sees the raw message. A follow-up reply gets its own filter — `is_junk_reply()`'s cheap pattern check first, then (only if that's inconclusive) an AI backstop (`_filter_substantive_context`) that judges whether a reply is a real, substantive answer or just filler ("nice," "ok," a repeated echo of the original question). Both exist because a merchant's reply that carries no real information should never be silently treated as if it answered the question.
- **The primary/fallback pattern**, described in §3, wraps every single AI call in this file — no step has to think about API reliability itself.
- **A real, wired LangGraph checkpointer that doesn't actually do anything yet.** `DisputeAgent` accepts one and compiles the graph with it (`self._graph.invoke(initial_state, config=config)`), and `api_server.py` does construct a real one on startup. But the browser never resends the `thread_id` needed to resume from it — every call effectively starts a brand-new conversation from the checkpointer's point of view. Multi-turn memory in this app comes entirely from the browser re-sending the accumulated conversation text as `additional_context`, not from anything this file persists on its own. Full detail in `LANGCHAIN_LANGGRAPH_GUIDE.md` §2.7.
- **A simple response cache** (`self._list_cache`) remembers recent list/comparison-style answers by their exact query text, so asking the identical question twice in a row doesn't re-run a full search-and-generate cycle.
- **A hard cap on how many clarification rounds a conversation can go through.** Every other loop in this graph already had a termination guarantee (evidence-gathering self-limits to one follow-up round, settlement detection asks once, reflect_node isn't a cycle at all) — the ask-merchant loop as a WHOLE was the one exception: nothing bounded how many rounds of "still don't have enough, ask again" a conversation could go through in total, across different question types (ambiguous case reference, missing reason code, missing evidence, settlement ambiguity). `MAX_CLARIFICATION_ROUNDS = 3` fixes that: once a conversation has gone three rounds without resolving, `_ask_user_node` (the single funnel for the main pipeline's asks) and three of `_validate_node`'s own early-return asks (out-of-range case reference, relative case reference, ambiguous new-topic) all switch to a fixed escalation message telling the merchant to share the chargeback notice or contact their bank directly, instead of asking a fourth time. `classifier.count_clarification_rounds()` computes the round count fresh on every call, purely from `additional_context` — this project's only cross-call memory (see the checkpointer note above) — rather than trying to increment/persist a counter that the stateless-per-call client has no way to round-trip. First attempt at that function tried to exclude "clarification about the question" replies (e.g. "where do I find the reason code?") from the count, reusing `is_clarifying_question()` — reverted after confirming live it was actively wrong: a genuine unresolved primary reply like "what about the other one?" also ends in "?", so the exclusion matched it too, and a merchant repeating exactly that phrase kept the round count stuck at 0 forever, silently defeating the cap for the exact ambiguous-case-reference scenario it exists to bound. Every non-empty reply segment counts now, full stop — a real meta-question costs one of the three rounds it didn't need to, a deliberate, documented trade-off in favor of a cap that can't be talked past by phrasing. `clarification_reason` (one of four `CLARIFICATION_REASON_*` constants, or `""`) is set alongside each ask — though it's known to go stale in at least one path (a settlement question resolved in one round can still show `settlement_ambiguity` on the terminal, already-answered turn) since not every downstream node resets it; a real gap, left as-is since it doesn't affect behavior beyond telemetry/UI accuracy for that one stale-value case.

Originally this field was pure telemetry, not read by any routing logic — no longer true. `needs_more_info` turned out to be overloaded for two different things: "the merchant must answer something" and "keep `pendingQuery`/`additional_context` alive client-side for a natural follow-up" (e.g. `_build_case_intro()`'s progressive introduction, or `_answer_clarification_node`'s answer to a meta-question — both set `needs_more_info: True` purely for the second reason, with no literal question in the text). `chat.html`'s follow-up bubble assumed the flag always meant the first, so a complete, confident case summary or "we already have what's needed for this case" answer got wrapped in the "I need a bit more information before I can help" banner — confirmed live: a merchant asking "why are you recommending a rebuttal letter?" got exactly that contradiction. Fixed by having `chat.html` read `clarification_reason` (non-empty = a real pending question, `""` = a complete answer that merely keeps the thread alive) to choose the bubble style, while `needs_more_info` keeps its original job of driving `awaitingContext`/placeholder text. Two call sites' `clarification_reason` values were corrected to make this distinction actually hold: `_build_case_intro()`'s two return paths in `_validate_node` now report `""` instead of `CLARIFICATION_REASON_MISSING_EVIDENCE` (the intro doesn't ask anything itself), and `_answer_question_node`'s personal-data list branch now reports `CLARIFICATION_REASON_AMBIGUOUS_CASE_REFERENCE` (it does end by asking the merchant to pick a case). `_ask_user_node` also stopped forcing `needs_more_info: True` when `answer_clarification_node` already reported `ledger_decision` set — that combination means the bank's own ledger already settled the case, so nothing is actually pending.

**A deeper bug in the same trace, once the banner stopped lying: the underlying "fight" recommendation itself was a causal leap the evidence never actually supported.** The merchant's next question — "what if any intermediate party would have charged customer?" — was the correct challenge, not a stalled conversation. `chargeback_analysis.py`'s U002 branch was inferring "customer wasn't double-charged" from "merchant's ledger, reconciled against network settlement, shows one credit" — but that only proves what reached the MERCHANT; a duplicate debit could occur upstream (a PSP/intermediary layer) and be reversed, or worse, succeed without its credit ever landing in this merchant's ledger at all, and neither `count_credits()` nor `reconcile_utr()` can see either case. Two things were wrong at once, and both had to be fixed together for the merchant's real question to get a real answer: (1) the round cap fired on this exact question — it was the 3rd reply segment, so `_ask_user_node` discarded `_answer_clarification_node`'s already-computed answer and returned the generic "I still don't have enough information, contact your bank" escalation instead, purely on segment count, with no regard for content; fixed by exempting `merchant_is_asking_question` turns from the cap (`count_clarification_rounds()` still counts them, so a genuine mix of stalling AND meta-questions still eventually caps on the evidence-ask side — this only stops a real, already-answered question from being overwritten). (2) Even un-discarded, the answer would have been honest but toothless ("I don't have that information") because the system had never actually checked. Fixed by adding `cbs.py`'s `network_debit_attempts` table + `get_debit_attempt_status()` — a second, genuinely independent (simulated) data source answering the customer-side half of the question that `reconcile_utr()` structurally cannot — and wiring it into `analyze_chargeback()`'s U002 branch (see `DECISION_RULES_GUIDE.md` §6 and `chargeback_analysis.py`'s docstring, step 2c): no network record yet downgrades "fight" to "cannot confidently decide" (`source="network"`, routed through the same `ledger_no_decision_reason` no-evidence-ask path as a settlement mismatch — `chargeback_agent.py`'s source tuple was extended to include `"network"`); a confirmed, unreversed second debit attempt flips the recommendation to `"refund"` outright, since the customer's claim is then true at the network level regardless of what the merchant's own ledger shows. Verified live: replaying the exact reported case now answers "what if an intermediate party charged the customer?" (as the 3rd reply segment, `clarification_round: 3`) with the network's actual finding — "the network and the merchant's ledger each show only a single debit... no evidence of any intermediate party having made an additional charge" — not an escalation message.

**A related but distinct bug in the same conversation family, found immediately after fixing "help me with it" -> "please describe a chargeback dispute" (see the `looks_like_new_request()` fix above): once that rejection stopped happening, "help me with it" instead skipped straight to a complete, formal rebuttal letter — the exact same output an explicit "give me a resolution" would produce.** `_extract_evidence_node`'s `ledger_decision` shortcut had always fired unconditionally the moment a case's outcome was already known deterministically (see this file's ledger_decision discussion above) — it was BUILT to skip pointless evidence-gathering for a bank-evidence-backed case, but nothing in it actually distinguished "the merchant explicitly wants the decision now" from "the merchant said literally anything non-question-shaped." Since `_build_case_intro()` always shows a summary first (this file, above) before any turn can reach this shortcut, that summary already told the merchant what evidence mattered — a vague, confirming "help me with it" doesn't mean "skip straight to a formal legal document," but the shortcut couldn't tell the difference. Fixed with `classifier.looks_like_explicit_resolution_request()` (patterns like "give me a resolution," "go ahead," "draft the letter," "fight it") gating the shortcut: an unambiguous ask still proceeds straight through exactly as before; anything else gets a short, two-option scoping question (`CLARIFICATION_REASON_UNCLEAR_HELP_SCOPE`) — "Want me to explain the evidence in more detail, or should I go ahead and draft the response now?" — capped by the same `MAX_CLARIFICATION_ROUNDS` as every other ask in this graph.

The first implementation of this gate looked at `state["additional_context"]` directly inside `_extract_evidence_node` and didn't work at all — confirmed live before shipping it. `_validate_node`'s own Guard 5b (`_filter_substantive_context`, an LLM call judging whether a reply is *evidence*) correctly judges "help me with it" as non-substantive — it describes nothing that happened — and blanks `additional_context` to `""` before `_extract_evidence_node` ever runs. By the time the gate checked it, there was nothing left to check, so it silently fell through to the unconditional bypass every time, regardless of what was actually typed. Fixed by computing `explicit_resolution_requested` once in `_validate_node`, from the RAW latest reply segment — BEFORE the evidence-substantiveness filter can touch it — and threading it through `ChargebackState` as its own field for `_extract_evidence_node` to read directly, the same pattern `merchant_is_asking_question` already uses. Two different questions ("is this evidence" vs. "did they ask for the decision") need two different filters; reusing one node's already-filtered output for the other node's unrelated question was the actual bug, not the regex itself.

**A fourth bug, this time in the case FACTS themselves, not the routing around them.** A merchant asked "what is resolution of NPCI20260530M002010?" and got back "the system's recommendation is to fight the dispute... We already have all the needed information for this case." Reported live as a real failure, for good reason: "resolution" and "recommendation" are different things — a recommendation is this system's advice, a resolution is whether the case is actually closed — and the answer read as substituting one for the other. Traced with LangGraph's `.stream()` (not `run()`, which only returns the final state) to see which node actually produced it: `_answer_clarification_node`, fed by `_planner_node`'s case-lookup `status_line` — which turned out to be the real root cause. That string blended case status, resolution status, and recommendation into one run-on sentence ("Current status: Open, resolution: not yet resolved") and never included the response deadline AT ALL, despite `_deadline_bucket()` already existing elsewhere in this file (used for the open-case list's urgency summary) specifically to compute "has this deadline passed" — so even though the merchant's OWN listing a turn earlier had correctly flagged this exact case "DEADLINE PASSED," the fact string feeding the direct answer had no way to mention it, and didn't. The LLM was reasonably synthesizing a blended answer from an already-blended fact — this wasn't a prompt-following failure. Fixed at the data layer, not just the prompt: `status_line` (and `_lookup_case_details`'s matching tool-call content, used by `_build_case_intro`) now states case status, resolution status, and deadline (with a passed flag from `_deadline_bucket()`) as three explicitly separate, individually-labeled facts — plus a stronger system-prompt instruction spelling out that these, together with recommended action, are four separate things never to merge, and that a "you already have what's needed" close must name every check the record actually cites (both ledger AND network, when both are present) rather than asserting confidence without showing it. Verified live, 3/3 identical repeats: the same question now returns cleanly separated case status / resolution status / recommended action / deadline-passed fields, citing both the ledger and NPCI/PSP checks by name.

**A fifth bug, found immediately after the fourth: "leading with case facts" doesn't know when NOT to.** With a case already anchored, "Does U002 mean the customer won?" — a generic, conceptual question with no "this case" and no case ID in it — got back the SAME full case-status recap as a direct case-specific question, instead of a short "no, it's a reason code, not an outcome." `_answer_clarification_node`'s "lead with case-specific facts" instruction (added for the fourth bug and its predecessors) had no signal to turn itself off once a case was anchored — every question got the case dump, whether it was actually about the case or not. Fixed with `is_case_specific_question`, reusing `classifier.refers_to_current_case()`/`extract_case_reference()` — the same deterministic signals `_validate_node` already trusts for this exact distinction elsewhere in this file — to gate BOTH the lead-in instruction (case facts vs. a plain conceptual answer) and the closing instruction (case-specific evidence talk vs. a direct answer with no case reference at all). Verified live: the same question, same anchored case, now answers "No. A U002 reason code simply indicates the cardholder is alleging a duplicate charge. It does not automatically mean the customer wins..." in 3 sentences, with zero mention of the anchored case; a genuinely case-specific follow-up ("what is the resolution of this case?") on the same conversation still gets the full, correctly-separated status/resolution/recommendation/deadline answer, unaffected.

One more thing surfaced in the same report, worth recording even though it wasn't a bug: a message that got back "I can only answer questions about your chargeback data. Try: 'show open cases'..." mid-conversation wasn't a dispute-agent failure at all — that string only exists in `text_to_sql.py`, the separate "My Chargebacks" tab's NL-to-SQL layer (`api_server.py`'s `/query` endpoint). `chat.html`'s three tabs (Q&A Search, Dispute Assistant, My Chargebacks) each call a completely different backend with no cross-routing (`switchTab()` sets `currentTab`, and the send handler branches on it directly) — so that response means the message was sent while the "My Chargebacks" tab was active, not the "Dispute Assistant" tab the rest of the transcript was on, not a routing bug inside either individual tab.

**A sixth bug, and the sharpest one yet: the response deadline was mentioned everywhere but acted on nowhere.** Every answer this file's fourth/fifth bugs fixed correctly SAID "the response deadline has already passed" — and yet the recommended action stayed a flat "fight, submit evidence," identical to what it would say if the deadline were a month out. Reported live, bluntly: "why is not checked that due date is already expired?" — a fair question, because it genuinely wasn't; `deadline_bucket()`'s "overdue" classification only ever fed decorative prose, never `chargeback_analysis.py`'s actual recommendation logic, which had zero awareness of dates at all. Fixed by making `Analysis` (the `chargeback_analysis.py` NamedTuple every recommendation flows through) carry a real `deadline_expired: bool` field, computed once per case and returned from every branch — including the `action=None` ones, since an expired deadline is a fact about the CASE, independent of whether a confident fight/refund recommendation exists. `deadline_bucket()` itself moved from `chargeback_agent.py` to `merchant_db.py` to make this possible without a circular import (`chargeback_analysis.py` -> `cbs.py` -> `merchant_db.py`; `chargeback_agent.py` -> `chargeback_analysis.py` — `merchant_db.py` is the only module low enough in that graph for both to reach it). The new field threads through as `ChargebackState.case_deadline_expired`, set alongside `ledger_decision`/`case_intro_action` in both places a case gets resolved (`_planner_node`'s lookup, `_build_case_intro()`), and is checked at three points that actually change behavior, not just wording: `_answer_clarification_node` gets a dedicated closing instruction ("do NOT present evidence submission as routine... recommend contacting the acquiring bank/PSP immediately") that fires ahead of the normal ledger_decision one; `_build_case_intro()`'s system prompt is told to state a passed deadline near the top, not bury it; and `_generate_node` deterministically PREPENDS a `⚠️ IMPORTANT` warning to the drafted letter itself whenever the deadline has expired — not left to the LLM's own prompt-following, the same reasoning the disclaimer guardrail right below it already uses. Verified live: the same case's intro, direct "what is the resolution" answer, and generated rebuttal letter all now lead with the deadline warning and recommend contacting the acquiring bank/PSP, instead of presenting evidence submission as routine.

**A seventh bug, found while stress-testing a long, realistic conversation against a merchant-supplied ideal script: `count_clarification_rounds()` counts EVERY reply segment in the whole conversation, with no regard for topic — so a long, healthy, wide-ranging generic Q&A exchange (six turns about what U002 means, what evidence is needed, whether the merchant can win) reliably pushes `clarification_round` past `MAX_CLARIFICATION_ROUNDS` before the conversation ever reaches its first real case-specific ask.** When the merchant finally supplied a real case ID on turn 6 and `extract_evidence_node`'s scoping question (added the previous session — "want me to explain the evidence, or draft the response?") fired for the very FIRST time, `_ask_user_node` crushed it with the generic "I still don't have enough information... contact your bank" escalation, purely because the round count was already 6 — despite that scoping question never having been asked before, let alone ignored three times. The round cap's own justification (bound a conversation that ISN'T making progress) doesn't hold here: the conversation was making plenty of progress, just about other things. Fixed with the same shape of exemption `merchant_is_asking_question` already has: the cap does not apply when `clarification_reason == CLARIFICATION_REASON_UNCLEAR_HELP_SCOPE` — a merchant who stays vague specifically in response to THIS scoping question, repeatedly, could in principle still loop, accepted as the smaller risk against a healthy conversation dead-ending on its very first ask. Verified live by replaying the exact reported 7-turn sequence: the scoping question now fires correctly instead of the escalation message.

**An eighth bug, surfaced by chasing the seventh one down: `chargeback_agent.py` calls `text_to_sql.query_chargebacks()` directly (code reuse, not an HTTP hop) from four places when it detects a data-lookup intent — and none of them could tell a real, SQL-derived answer apart from that function's own "this isn't actually a data question" bail-out, since both come back in the identical shape (`error=""`, `answer=<text>`).** Confirmed live: replaying the same 7-turn sequence one step further (replying "Yes." to the scoping question), one of these four call sites fired, `query_chargebacks()` internally decided the pending question ("What is the resolution of U002 cases?") wasn't a real data lookup, and its own tab-specific "I can't answer that here — try the Dispute Assistant tab" bail-out text got surfaced AS the Dispute Assistant's own answer — nonsensically telling the merchant to go to the tab they were already in. This gap predates this session, but the sixth bug's own fix (giving that bail-out message specific, named tab-navigation text) is what made it glaringly visible instead of just generically unhelpful. Fixed at the source: `query_chargebacks()`'s Step 0 conversational bail-out now returns `"conversational": True`, and all four `chargeback_agent.py` call sites check it before trusting `result["answer"]` — the two deterministic short-circuits (`looks_like_aggregate_question`/`looks_like_status_question`) and the LLM-tool-call branch (`query_chargeback_data`) all return `None` instead (falling through to normal, non-data-lookup handling), and `_planner_node`'s "Merchant history" RAG-context append skips it entirely rather than feeding a tab-navigation message into the case's own retrieved context. Verified live: the same reply now falls through to a genuine, honestly-hedged conceptual U002 answer instead of the self-referential tab message.

**A ninth bug — the sixth bug's own fix over-corrected: it added a deadline-passed warning without ever removing the ROUTINE content it was warning against.** `_build_case_intro()`'s system prompt got a bolt-on instruction ("state the deadline plainly near the top") layered on top of its *original*, unconditional instruction ("write a summary covering what the reason code means and what evidence is needed next") — so the LLM correctly did both, producing a warning banner, the FULL normal reason-code explanation and evidence checklist exactly as if the case were still active, then a second deadline reminder at the end (echoing `_lookup_case_details`'s own tool-content "IMPORTANT" note). Reported live as visibly buggy, and rightly so: a merchant reading it sees the same "your window may be closed, contact your bank" message bookending a full "here's what to submit" walkthrough that directly contradicts it. Fixed by replacing the bolt-on with two genuinely exclusive output shapes the prompt names explicitly — shape 1 (deadline not passed) is the original full walkthrough, unchanged; shape 2 (deadline passed) is a hard STOP after three lines: the fact, the case identifier, and the one urgent instruction — with an explicit "do NOT also give the full reason-code explanation... do NOT repeat the deadline warning at the end" rule, since layering a warning ON somewhere in the *content* doesn't stop the LLM from independently reaching for its other instruction to write the routine summary too. Verified live: the same case's intro dropped from a 3-section walkthrough sandwiched between two deadline warnings to 3 clean lines; a genuinely non-expired U002 case (2026-09-23 deadline) still gets the original full shape-1 walkthrough, unaffected.

- **Every live-chat recommendation is persisted, not just returned and forgotten.** Two background pollers (`auto_decision_poller.py`, `suggestion_poller.py`) already wrote `chargebacks.suggested_action`/`suggestion_reason` from their own periodic, evidence-BLIND (CBS/ledger-only) analysis via `chargeback_analysis.analyze_chargeback()` — but a live conversation's own recommendation, which can incorporate real evidence the merchant just supplied, was never recorded anywhere; it only ever reached the merchant in that turn's HTTP response. Fixed by wiring persistence into `DisputeAgent.run()`, once, right after `self._graph.invoke()` returns — not as a new graph node, since `thread_id`/`merchant_id` are `run()`-scope parameters, never part of `ChargebackState`, and `run()` is the sole call site for the compiled graph across the whole codebase. Two distinct recommendation-producing paths both feed into it: the main pipeline's evidence-informed `decision`/`decision_reason` (from `decide_node`, tagged with a new `decision_source` — `"ledger"`/`"rules"`/`"llm"`, set alongside `decision` at its three real decide sites), and `_build_case_intro()`'s evidence-BLIND preview (`case_intro_action`/`case_intro_reason`/`case_intro_source` — the same CBS/ledger-only view the background pollers already act on, surfaced live before any evidence-gathering happens; this path never reaches `decide_node` at all, so the two are mutually exclusive by construction — `decision` stays `""` whenever `case_intro_action` is set, and vice versa). Both funnel through one new method, `_persist_recommendation()`, which is a hard no-op unless the action is a real `"fight"`/`"refund"` and a real `case_id`/`merchant_id` are both known — never fires for a generic Q&A turn, a list-only turn, or an ask-user turn with nothing decided yet. New module `case_recommendations.py` owns the actual writes: one `INSERT` into a new, append-only `case_recommendations` table (real queryable history — `guardrails.AuditLogger`'s `audit.log` is append-only JSONL, good for compliance review, not joinable/queryable) plus one `UPDATE` refreshing `suggested_action`/`suggestion_reason` to match, in the same connection/commit. **Hard safety constraint, enforced at the SQL level and covered by a dedicated regression test:** this write path can *never* touch `chargebacks.status`/`resolution`/`resolution_date` — those are reserved for the merchant's own confirmed action or `auto_decision_poller.py`; a live-chat recommendation is advice, never an action taken on the merchant's behalf, mirroring the exact same distinction the schema already draws between the two existing pollers. Two new read-only endpoints (`GET /case-recommendations/{case_id}`, `GET /case-recommendations`) expose the history with the same role-scoping `/my-open-chargebacks` and `text_to_sql.py` already use — a merchant only ever sees their own case's history (a mismatched case_id returns an empty list, never confirming or denying it exists), admin roles see any case or merchant.

## Two full traces, from the merchant's first message to the final answer

**Trace 1 — a straightforward new dispute:** *"Mastercard chargeback, customer says the charge is fraudulent, but they placed the order through our 3D Secure checkout."*

1. `validate` — passes the safety checks, no prior conversation context, classified as `"dispute"`.
2. `planner` — pattern-matching finds `"Mastercard"` but no specific 4-digit code in the text; retrieves relevant Mastercard fraud policy anyway via similarity search.
3. `detect_settlement` — not a settlement issue; this is a real dispute.
4. `extract_code` — still no code known, and no follow-up reply yet to check → the conversation pauses here, asking for the specific reason code.
5. `ask_user` — returns the question. **Turn ends.**

Second message: *"4837, and yes we have 3DS authentication logs."*

6. `extract_code` — now finds `"Mastercard 4837"` in the reply.
7. `detect_clarification` — this isn't a question, it's an answer → proceeds to evidence extraction, not clarification.
8. `extract_evidence` — the rule table already knows 4837 needs `avs_match`/`cvv_match`/`three_ds_authentication`; recognizes "3DS authentication logs" as exactly that.
9. `decide` — the rule table has a direct answer for Mastercard 4837 with 3DS confirmed: **fight**, no AI judgment call needed.
10. `generate` — drafts the rebuttal letter, pulling in a real example rebuttal structure from the knowledge base, appends the standard disclaimer.
11. `reflect` — checks the draft only cites "4837," which is both the case's own confirmed code and present in the retrieved docs → grounded. Computes a high confidence score (a matched rule-table entry plus real evidence tags). **Turn ends — merchant sees the finished letter.**

**Trace 2 — a conversational case exploration:** *"show me my open chargebacks"* → *"tell me about the first one"*

1. `validate` — first turn, no prior context, classified as `"question"` (a data-lookup request, not a specific dispute description).
2. Routes to `answer_question` — recognizes this as asking about the merchant's *own* data, and the tool-calling decision (§6) picks "list my cases." Renders the real open cases from the database, soonest deadline first, and asks which one to discuss. **Turn ends.**

Second message, same conversation:

3. `validate` runs again — this time `additional_context` holds "tell me about the first one." The continuity logic (§6) resolves "first one" against the case list, positively identifies a real case, and calls `_build_case_intro()` — which itself makes two rounds of real database + knowledge-base lookups (case details, then that reason code's requirements) before synthesizing one grounded answer.
4. `validate_node` returns **immediately** with that full answer — `planner`, `decide`, `generate`, and every other step in the main pipeline never run for this turn. **Turn ends — merchant sees a real case summary, what the reason code means, and what evidence is needed, all in one response.**

## Design philosophy — why it's built this way

A few decisions repeat throughout this file, worth naming explicitly:

- **Deterministic before AI, wherever the task allows it.** Reason-code pattern matching, fight/refund decisions for known codes, and "is this a settlement issue" are all plain Python — faster, free, and testable with an ordinary assertion, not just "looks reasonable." AI calls are reserved for genuinely open-ended judgment (does this reply actually answer the question, what does this specific reason code's evidence requirement look like in this merchant's own words, write a persuasive letter) — and even there, the model is given as much structure as possible (a closed evidence vocabulary, rule-scoped guidance, JSON-only responses) rather than being asked to freelance.
- **One job per step, routing kept completely separate from logic.** No step in this file decides what runs next — that decision lives only in dedicated `_route_after_*` functions. This means you can read any one step in isolation and know exactly what it does, without needing to also trace where control might jump afterward.
- **Every AI-calling step gets its own narrow persona.** "Chargeback evidence analyst" here, "chargeback strategy consultant" there — never one general-purpose assistant character carried across the whole file. A narrowly-scoped job is both easier for the model to do reliably and easier for a human reviewing the prompt to reason about.
- **Verification is deterministic, deliberately.** `reflect_node` — the step whose entire job is "can we trust this answer" — calls no AI model at all. Using the same kind of system that might make something up to also certify that it didn't would defeat the point.
- **Known limitations are documented, not hidden.** The inert checkpointer (§7) and the conversational-memory gap (§6) are both real, current limitations of this file's design — recorded here and in the related guides specifically so a future reader doesn't have to rediscover them the hard way.
- **A failed or ambiguous decision surfaces as "I'm not sure," never as a silent guess.** `_uncertain()` is the one shared method every node in this file reaches for when it can't confidently commit to an outcome — instead of each node inventing its own default. Three real instances of the same anti-pattern lived here before it existed: `_validate_node` silently treating an unrecognized case-anchored follow-up as evidence, `_decide_node` defaulting an unparseable response to "fight" (the *wrong* direction — this project's own `decision_rules.py` philosophy is "no evidence → refund," the safe default), and `_extract_evidence_node` defaulting an unparseable response to `needs_more_info=False`, silently letting an incomplete case proceed. This principle has a real limit, found live the same day: it only applies where there's genuinely no good default to fall back on. `_validate_node`'s first attempt at this went too far — an unconditional "ask when nothing else matches" rule also caught ordinary evidence text with no reason to be suspicious (an evidence answer is free-form "here's what I have," not a fixed phrase, so it can't be positively distinguished from a confusingly-phrased new topic by a keyword check) — and had to be walked back to only the narrower, specifically-justified cases. Not every ambiguity deserves a clarifying question; only the ones where guessing is worse than asking.
- **Decision shape is enforced by a schema, not a naming convention.** `decide_node`'s fight/refund/uncertain output is a real Pydantic model (`DecisionOutput`) passed through a new `_invoke_structured()` method — LangChain's `.with_structured_output()`, with the same primary→fallback contract `_invoke()`/`_invoke_with_tools()` already use — instead of a free-form JSON string parsed by `guardrails._parse_json_safe()` and defensively `.get(..., default)`'d afterward. The two approaches were producing the identical *decision shape* already; the schema just makes the constraint real and provider-enforced instead of a convention every call site has to independently get right. Verified live across both directions — strong evidence correctly returns `fight`, no evidence correctly returns `refund` — confirming the schema doesn't just look right, it round-trips through `generate_node`/`reflect_node` the same way the old free-text version did. Converted `decide_node` first, as the highest-value single case, not a wholesale rewrite of every `_invoke()` call site in this file at once.
