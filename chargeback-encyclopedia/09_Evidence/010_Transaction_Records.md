# Transaction and Authorization Records

## What Are Transaction and Authorization Records?

Transaction and authorization records are the foundational documentary evidence for every chargeback response. They prove that a transaction was processed, authorized by the card network, and settled correctly. Without these records, a merchant cannot establish the basic facts of any dispute.

Authorization records are generated at the moment a card is approved for a transaction. Settlement records are generated when that approved transaction is actually captured and submitted for payment. Together, they document the complete lifecycle of a payment from approval to funding.

Understanding what data these records contain — and where to find it — enables merchants to present professional, complete transaction evidence rather than incomplete screenshots of order management systems.

## Components of an Authorization Record

When a cardholder's card is presented for payment, your payment processor sends an authorization request to the card network. The network forwards it to the issuing bank. The issuer approves or declines and returns a response. All of this occurs in 1–3 seconds. The response record contains:

### Authorization Code
A 6-character alphanumeric code (e.g., "TH3K9F") returned by the issuing bank confirming the transaction is approved. This is the single most important element of an authorization record — it proves the issuer approved the transaction.

**In dispute evidence:** "The transaction was approved by the issuing bank with authorization code TH3K9F, as shown in the authorization record (Exhibit A). The issuer had the opportunity to decline this transaction and did not do so."

### AVS Response Code
The result of the Address Verification Service check (Y, A, Z, N, U, etc.). See 09_Evidence/002_AVS_Address_Verification.md for code definitions.

**In dispute evidence:** "The address verification check returned code Y (full match), indicating the billing address and ZIP code provided by the customer matched the issuing bank's records."

### CVV Response Code
The result of the CVV2 verification check (M, N, P, etc.). See 09_Evidence/003_CVV_CVC_Verification.md for code definitions.

**In dispute evidence:** "The card verification value (CVV2) was verified at authorization and returned a match code (M), indicating the card's printed security code was correctly provided."

### Transaction Amount and Currency
The exact authorized amount and currency code (USD, EUR, GBP, etc.). For disputes involving amount mismatches (Visa 12.x series, Mastercard 4831), this is critical — the authorized amount must match the settled amount, or you must explain any differences (incremental authorizations, tips, etc.).

### Transaction Timestamp
Date and time of the authorization, in the processor's timezone (typically UTC or Eastern Time). For friendly fraud disputes, the authorization timestamp confirms when the transaction was placed and can be correlated with login logs, IP address capture, and delivery timestamps.

### Merchant ID (MID)
Your merchant identifier — the number assigned to your merchant account by your acquiring bank. This uniquely identifies you as the merchant in all network records. Include this in dispute submissions so the issuer can cross-reference against their network records.

### Terminal ID (TID) — For Card-Present Transactions
For card-present (in-store) transactions, the Terminal ID identifies the specific POS terminal that processed the transaction. This is relevant for disputes involving terminal-based processing issues (chip read failures, fallback transactions, etc.).

### Card Information (Masked)
The authorization record shows the card number in masked format (first 6 and last 4 digits: `411111XXXXXX1111`) along with the card expiration date and card type (Visa, Mastercard, Amex). Confirm that:
- The card expiration date at time of transaction was in the future (card was valid).
- The card BIN (first 6–8 digits) matches the issuing bank the dispute is coming from.
- The card type matches the dispute type.

### Acquirer Reference Number (ARN)
The ARN is a unique identifier assigned to the transaction by the acquiring bank. It allows any party in the payment chain (issuing bank, network, merchant) to look up the specific transaction in network records. Always include the ARN in your dispute submission.

### Network Reference / Retrieval Reference Number (RRN)
A transaction reference number generated by the card network. Used for retrieval requests (the step before some chargebacks) and for cross-referencing in network records.

## Settlement Records

A settlement record documents the actual capture and funding of an authorized transaction. Not every authorization becomes a settlement — if an order is cancelled before settlement, no settlement occurs.

Settlement records contain:
- Settlement date (which may differ from authorization date for pre-authorizations or deferred captures).
- Settlement amount (must equal the authorized amount, or incremental authorizations must be accounted for).
- Settlement batch ID.
- Funding date (when the proceeds were credited to your bank account).

**Relevance to disputes:**
- Processing error disputes (Visa 12.x, Mastercard 4831) often involve discrepancies between authorization and settlement amounts. The settlement record proves the settled amount.
- For "transaction not authorized" disputes, showing the settlement occurred confirms the card was actually charged, not just authorized.
- For credit not processed disputes (Visa 12.7), settlement records can confirm whether a refund was submitted.

## What to Pull from Your Payment Gateway or Processor

Most payment gateways and processors provide transaction detail views accessible through their merchant portal. The specific navigation differs by provider, but all major platforms provide:

**Stripe:** Dashboard → Payments → [specific payment] → View all details. Includes auth code, AVS result, CVV result, risk score, and full timeline.

**Braintree:** Control Panel → Transactions → [Transaction ID]. Shows auth code, AVS/CVV results, processor response, and settlement status.

**Authorize.Net:** Merchant Interface → Reports → Transaction Detail Report. Exportable to CSV with auth codes and response data.

**PayPal/Braintree:** Transaction Detail includes AVS, CVV, authorization code.

**Square:** Dashboard → Sales → Transactions → [Transaction]. Shows card details, auth code, and risk information.

**Adyen:** Customer Area → Transactions → [PSP Reference]. Provides authorization data, AVS/CVV, 3DS result, and settlement data.

**First Data / Fiserv, Chase Paymentech, TSYS:** Access through processor reporting portals or contact your account representative for transaction detail exports.

When submitting as dispute evidence, export as PDF or CSV and annotate the key fields (auth code, AVS, CVV) for the issuer analyst.

## How to Present Authorization Data to the Issuer

**Standard authorization record exhibit:**

```
Transaction Authorization Record (Exhibit A)

Merchant:              [Your DBA Name]
Merchant ID (MID):     [MID]
Transaction Date:      March 15, 2024 at 14:32:07 UTC
Transaction Amount:    $247.00 USD
Card Type:             Visa
Card (masked):         411111XXXXXX1111
Card Expiry:           09/2026 (valid at time of transaction)
Authorization Code:    TH3K9F
AVS Response:          Y (Full match — street and ZIP)
CVV Response:          M (Match)
3DS ECI Code:          05 (Full Authentication)
CAVV:                  [CAVV Value]
ARN:                   [Acquirer Reference Number]
Settlement Date:       March 16, 2024
Settlement Amount:     $247.00 (matches authorization)
Settlement Status:     Funded
```

This single exhibit establishes all authorization-level facts. Cross-reference it in your rebuttal letter: "As shown in Exhibit A, the transaction was authorized by the issuing bank (auth code TH3K9F), with matching AVS and CVV results and successful 3DS authentication."

## Mismatch Between Authorization and Settlement

If the settlement amount differs from the authorization amount, you must explain the difference in your rebuttal or the issuer may cite it as a processing error.

Legitimate reasons for amount differences:
- **Tips or gratuity:** Restaurant transactions where the authorized amount is the food total and the settled amount includes tip.
- **Incremental authorizations:** Hotel, car rental, or other merchants who add charges incrementally.
- **Currency conversion:** Dynamic currency conversion may result in minor rounding differences.
- **Partial captures:** Settling a portion of the authorization when only part of the order ships.

For any amount mismatch, document the reason with a supporting exhibit (tip receipt, incremental authorization record, shipping partial fulfillment record).

## Card Expiry at Time of Transaction

Confirming that the card was not expired at the time of the transaction is a basic but important check. An authorization cannot complete with an expired card — the issuer will decline it. If the authorization succeeded, the card was valid at authorization time.

Include the card expiry date (masked, showing only month/year: "09/2026") in your authorization record exhibit to confirm validity.

## Summary

Transaction and authorization records are the evidentiary foundation of every chargeback response. They establish what was charged, when, to which card, with what fraud screening results, and how it settled. Pull these records from your payment gateway immediately upon receiving a chargeback notification — gateway portals may have limited historical access windows. Present authorization data in a structured, annotated exhibit format that highlights the authorization code, AVS/CVV results, and settlement confirmation. These records, combined with other evidence types (delivery proof, usage logs, device fingerprint), form the complete chargeback rebuttal package.
