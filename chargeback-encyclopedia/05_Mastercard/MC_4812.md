# Mastercard 4812 — Account Number Not on File

## Definition

Mastercard reason code 4812 is issued when an authorization was obtained for an account number that does not exist in the issuer's system, or when the transaction was settled against an account number that the issuer cannot match to any active cardholder account. In plain terms: the card number used in the transaction does not correspond to a valid account on the issuer's records.

This is primarily a technical or data integrity code rather than a fraud code. The cardholder may have intended to make the purchase, but the account number processed was incorrect, corrupted, or fictitious.

## When This Reason Code Applies

4812 chargebacks arise under the following conditions:

- **Data Entry Errors**: A cashier or customer manually entered a card number incorrectly (transposed digits, extra digit, etc.), and the number happened to pass the Luhn algorithm check but does not correspond to a real account.
- **System or Data Corruption**: A payment system or gateway garbled the card number during processing, resulting in an authorization request against an invalid account number.
- **Test Cards Used in Production**: A developer or tester used a test card number in a live production environment, and the transaction was settled.
- **Fictitious Account Numbers**: In rare cases, a fraudster presents a card number that passes initial validation checks but is not linked to a real issuer account.
- **Truncation or Padding Errors**: Middleware or processing systems that pad, truncate, or otherwise modify card numbers before transmission can generate invalid account numbers.
- **Closed Account Not Properly Flagged**: The account was closed and removed from the issuer's system but not yet removed from cached authorization files.

## Common Scenarios

**Scenario 1: Manual Entry Transposition**
A customer provides their card number verbally over the phone for a MOTO transaction. The operator enters "4532 1234 5678 9010" but the actual card number is "4532 1234 5678 9001." The transposed number passes the Luhn check, receives an authorization from the network (which may generate an approval based on BIN range routing), but cannot be matched to a specific account by the issuer upon settlement.

**Scenario 2: Gateway Data Corruption**
A payment gateway experiences a software bug that modifies the last four digits of card numbers during transmission. Transactions appear authorized, but when the issuer receives the settlement file, the account numbers do not match any cardholder records.

**Scenario 3: Developer Testing Error**
A new developer tests a payment integration in the production environment using the test card number "5105 1051 0510 5100." When the system attempts to settle this transaction, the issuer cannot locate the account and files a 4812 chargeback.

**Scenario 4: BIN Range Routing Issue**
An acquiring bank routes an authorization request based on the card's BIN (first six digits) to the correct network, but a downstream system error alters the full account number before it reaches the issuer. The issuer receives an authorization request for an account it does not recognize.

## Merchant Liability

Merchant liability for 4812 varies depending on the root cause:

- **Data Entry Error (Merchant's Fault)**: Full merchant liability. The merchant entered an incorrect number and settled against an invalid account.
- **System or Gateway Error**: Liability may be shared or shifted to the acquiring bank or payment processor if the error occurred in their systems. Document and escalate immediately.
- **Issuer System Error**: If the account number is valid and the authorization was correctly obtained but the issuer cannot find the record due to their own system issue, this may be a strong rebuttal opportunity.
- **Fraudulent Presentation**: If the customer presented a fictitious card number, the merchant may bear liability for failing to physically verify the card.

## Correction Steps

1. **Identify the source of the account number error**: Was it a manual entry error, system error, or external factor?
2. **Correct and re-process**: If the correct account number can be identified and the cardholder is legitimate, obtain the correct card information and process a new transaction.
3. **Void the errored transaction**: Cancel the settlement of the incorrect account number transaction to prevent further complications.
4. **Report to your payment processor or gateway**: If the error appears to be system-generated, report immediately so the processor can investigate data integrity issues.

## Required Evidence

To contest a 4812 chargeback (in cases where the merchant believes the chargeback is invalid), provide:

1. **Original Authorization Record**: The authorization log showing the account number, approval code, date, and time — exactly as submitted.
2. **Transaction Receipt or Order Confirmation**: Documentation linking the cardholder to the transaction.
3. **Gateway Processing Logs**: If the error is suspected to be a system/gateway issue, raw gateway logs showing the transaction data as transmitted.
4. **Correspondence with the Cardholder**: If the cardholder confirms the purchase and can verify their card details, a signed statement or email confirmation.
5. **Third-Party System Error Documentation**: If a processor or gateway error caused the account number corruption, a written incident report from that vendor.

## Winning Strategy

1. **Determine fault first.** Before drafting a Second Presentment, identify definitively where the account number error originated. If it is a merchant-side entry error, fighting the chargeback is unlikely to succeed.

2. **Leverage system error documentation.** If the error originated in the payment gateway or processor, obtain a written incident report from the vendor. This shifts liability away from the merchant and may result in the acquirer absorbing the loss.

3. **Match the authorization to the real cardholder.** If you can demonstrate that the authorization approval code was legitimately obtained and the error occurred downstream of the authorization, this is your strongest argument.

4. **If the issuer's system is at fault**, work with your acquirer to challenge the chargeback through formal channels, providing the authorization records as proof that the account number was valid at the time of authorization.

## Losing Mistakes

- **Ignoring the chargeback as a "system issue"**: Even legitimate system errors require a formal Second Presentment response. Silence results in automatic loss.
- **Submitting evidence for the wrong transaction**: Ensure all evidence references the specific transaction ID, amount, and date in dispute.
- **Failing to notify your processor**: If the error is processor-side, they may be obligated to absorb the loss — but only if you notify them promptly.
- **Re-processing without correcting the account number**: Submitting the same incorrect account number again compounds the problem.

## Prevention Checklist

- Use card-swipe, chip, or contactless entry for all in-person transactions — avoid manual key-entry whenever possible.
- For MOTO transactions, implement a read-back verification procedure: repeat the card number to the customer before processing.
- Conduct regular integration testing in a dedicated sandbox/staging environment — never use test cards in production.
- Monitor payment gateway software updates and perform data integrity checks after any system changes.
- Work with your processor to implement card number validation checks at the POS level before authorization requests are transmitted.

## Frequently Asked Questions

**Q: The cardholder insists they gave us the correct card number. Can we fight this?**
A: Yes, especially if you have documentation of what the cardholder provided. Include the order record, any written confirmation, and the authorization log. If the issuer cannot match the number, the error may be on their end or in transit — your rebuttal should make this argument clearly.

**Q: How do I know if the chargeback is due to my error versus a system error?**
A: Pull the raw transaction log from your payment gateway and compare the account number in the authorization request to the number on the customer's card or order form. If they match, the error is downstream. If they don't match, it is a merchant-side entry error.

**Q: Can a fictitious card number receive an authorization approval?**
A: In rare cases, yes. Some network-level authorization responses are generated based on BIN range routing before reaching the actual issuer. This does not constitute a valid authorization in the issuer's records, and 4812 can still be filed.

**Q: Should I contact the cardholder when I receive a 4812?**
A: If you believe the cardholder is legitimate and the error was a digit transposition, yes. Contacting the customer to obtain the correct card details can resolve the dispute without a formal chargeback fight and preserve the business relationship.
